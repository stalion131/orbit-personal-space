# Архитектурное решение: Orbit MVP с облачным доступом

## Текущий этап: папка исходных данных

[ADR-010](docs/ADR-010-project-source-folders.md): HTTPS-ссылка как реквизит проекта, выбор папки и файлов в браузере, защищённый локальный каталог по сохранённому пути. `GET /api/tasks/[id]/ppr-source-files` проверяет владельца/направление и реальные пути внутри разрешённой библиотеки и папки проекта. На Vercel локальный каталог отключён; произвольные внешние URL сервер не загружает. Ссылка исключена из контекста модели и снимка утверждения ТЗ. Форматы/лимиты разбора и отдельное согласие на SOL сохранены; миграций и новых зависимостей нет.

## Текущий этап: SOL и Word

Решение, библиотеки, модель хранения и ограничения: [ADR-009](docs/ADR-009-ppr-sol-word.md). Дополняет предыдущую форму ТЗ, не меняет роли остальных агентов.

## ADR 2026-09-04: единое ТЗ и рабочий экран

Согласованные требования и уточнённые правила разработки: `PPR_WORKFLOW.md`. Вместо двух пересекающихся форм используется одна форма из четырёх групп; ниже расположены четыре служебных блока, шаги и диалог рядом с широким документом. Все профессиональные роли остаются видимыми, в том числе неподключённые. Этап проекта задаётся вручную и не означает выполненную проверку.

Без новых зависимостей: используем существующие React 19, Next.js 16, Agents SDK 0.17 (MIT) и защищённые обработчики. Встроенных управляемых полей React достаточно для формы, новая библиотека форм или отдельная БД не требуются. Вспомогательные компоненты вынесены из `/work` в `components/work-*`; старый дашборд и его сортировка не меняются.

`WorkProject.brief` хранит указания, подписантов, реквизиты, перечень ТК/графиков и риски «да / нет / уточнить». Старые положительные флаги сохраняются, отсутствие отметки становится неизвестностью, а не подтверждённым отсутствием риска. Путь к рабочей папке — реквизит, не разрешение на доступ к произвольному каталогу. Неизвестные ФИО, полномочия и численность не выдумываются.

`POST /api/tasks/[id]/work-brief` проверяет владельца, направление, ревизию и подтверждение. `approve` добавляет снимок текущего ТЗ в `Task.briefApprovals` (до 10 редакций / 500 КБ), `prepare_tk` создаёт связанные задания в `Task.tkAssignments` по утверждённому перечню. Повторная операция отклоняется; задания пока не исполняются. Изменение содержательных вводных требует нового утверждения, изменение этапа, реестра или чек-листа — нет. Генерация и сохранение нового раздела также требуют актуального утверждения ТЗ. Старые версии остаются доступны. Это история MVP, не юридически значимая электронная подпись или защищённый архив.

Диалог расширяет существующую роль разработчика ППР вопросом и последними четырьмя обменами сообщениями. Каждый запрос требует отдельного согласия; отправляются паспорт и ТЗ с введёнными пользователем данными, включая подписантов. Содержимое файлов и рабочая папка не передаются. Снимки ТЗ сохраняются в той же задаче Supabase, без изменения RLS и миграций; без Supabase локальное хранилище остаётся временным. На Vercel доступ к диску компьютера не появляется.

Ограничения: извлечение и дозаполнение из исходных файлов, реальный исполнитель ТК, проверки НТД/качества, импорт исправленного DOCX, сохранение таблиц исходного шаблона и защита постоянных фрагментов ещё не подключены и отмечены в интерфейсе. Каркас предпросмотра с таблицей реквизитов не выдаётся за импортированный документ. HTML-версии разделов и существующая библиотека сохранены. Общий лимит импорта резервной копии — 2 МБ, его расширение требует отдельного этапа. Откат — возврат предыдущего коммита; новые поля JSON не требуют отката схемы.

## Цель этапа

MVP сохраняет задачи между устройствами, открывается по HTTPS-ссылке, устанавливается на телефон как PWA и содержит первого ИИ-агента для разбора задач. Внешние действия остаются за пределами этого этапа.

## Схема

```text
Браузер / установленная PWA
  ├─ Supabase Auth: сессия пользователя
  └─ HTTPS → Vercel / Next.js API + Bearer JWT
                           ├─ валидация и переходы задачи
                           ├─ OpenAI Agents SDK → структурированные предложения
                           └─ Supabase Data API → Postgres + RLS

Локальная разработка
  └─ тот же Next.js API → временное хранилище в памяти (только loopback)
```

Единственный рабочий публичный контур проекта — Vercel по постоянному адресу `https://orbit-personal-space.vercel.app`. Развёртывания Sites больше не используются; GitHub остаётся источником версии кода.

## Компоненты и ответственность

- **Dashboard:** React/Next.js, адаптивный интерфейс, вход, экспорт/импорт и PWA-установка.
- **Рабочий режим `/work`:** отдельный интерфейс разработки ППР и ТК. Он использует ту же сессию и API задач и показывает только задачи сферы `Работа`, закреплённые за направлением `ППР`. Карточка и паспорт проекта сохраняются в той же JSON-записи задачи; локальная библиотека доступна только с компьютера, а первый профессиональный агент подключён через защищённый серверный API.
- **Backend API:** `/api/config`, `/api/tasks`, `/api/tasks/:id`, `/api/import`; проверяет источник запроса, JWT, входные данные и ревизию задачи.
- **Supabase Auth:** email и пароль; токен пользователя передаётся API, пароль приложению не доступен.
- **Supabase Postgres:** таблица `orbit_tasks`. Политики RLS разрешают операции только владельцу строки. `anon` не имеет прав.
- **Локальное хранилище в памяти:** режим разработки. В облаке не используется и очищается после перезапуска.
- **Service worker:** кэширует только статическую оболочку. API, Supabase и страницы с данными всегда запрашиваются из сети и не записываются в Cache Storage.

## Модель и жизненный цикл данных

В Postgres хранятся `id`, `owner_id`, версионированный JSON-снимок задачи, `revision` и время обновления. Пользователь создаёт или изменяет задачу через API; сервер валидирует операцию; Postgres повторно ограничивает строку через `owner_id = auth.uid()`. Экспорт создаёт локальный JSON. Импорт принимает только формат `orbit-tasks-v1`, валидирует каждую задачу и сохраняет её текущему пользователю.

## Безопасность

- В браузере используется только publishable/anon key, который по модели Supabase является публичным. `service_role` не нужен и запрещён.
- Все таблицы публичной схемы защищены RLS и явными grants.
- Сервер сверяет JWT через Supabase Auth и передаёт тот же токен Data API, поэтому RLS остаётся последней границей доступа.
- Изменяющие запросы принимаются только от того же origin и с заголовком клиента.
- Задачи и ответы API имеют `Cache-Control: no-store`.
- Пароли, токены и ключи не сохраняются в репозитории и не выводятся в логи.

## ADR-001: Supabase как временное облачное хранилище

Рассмотрены: D1 без аккаунтов, Supabase, отдельный российский Postgres. Supabase выбран пользователем для MVP: официальный SDK, Auth, Postgres, RLS и простой перенос. Согласно официальному перечню регионов Supabase, российского региона нет. Поэтому перенос реальных персональных и рабочих данных в hosted Supabase и публичный запуск заблокированы до решения владельца о юрисдикции/трансграничной передаче либо выбора российского размещения. Код сохраняет локальный режим, поэтому решение обратимо.

Источник: Supabase Docs — Row Level Security, Auth, Available regions. SDK: `@supabase/supabase-js` 2.57.4, MIT.

## Границы этапа

Нет поисковых инструментов, почты, оплаты, бронирования, общего доступа к задачам, административной панели и Production SLA. Инструменты с побочным эффектом в будущих агентах должны только создавать предложение, а исполнение потребует серверно проверенного подтверждения.

Интерфейс ППР/ТК разделяет роли: разработчик ППР, разработчик ТК, специалист по НТД и контролёр качества. На текущем этапе активен только разработчик ППР; остальные карточки обозначены как следующие этапы и не создают ложных результатов. Подключение изменения исходных файлов и генерации документов потребует отдельного решения по рабочему хранилищу, модели документов и правам доступа.

## Карточка рабочего проекта

Направление `ППР` является системным элементом каталога и добавляется в существующий пользовательский каталог только при отсутствии направления с таким же названием. Это предотвращает дубли. Запись задачи остаётся источником срока, статуса и подзадач, а вложенный объект `workProject` хранит вид документа, объект, адрес, заказчика, ответственного и текущую стадию. Обновление выполняется через отдельную серверную операцию с проверкой принадлежности задачи направлению `ППР` и контролем ревизии.

Будущее файловое хранилище должно подключаться через отдельный адаптер. В задаче будут храниться только метаданные и ссылки, а содержимое файлов — у выбранного владельцем провайдера. До выбора провайдера кнопки загрузки остаются отключёнными.

## Реестр документов и чек-лист

Карточка рабочего проекта хранит два дополнительных массива внутри JSON задачи: `documents` содержит только метаданные документа (название, категория, версия, состояние и время изменения), а `checklist` — пункты готовности и их отметки. Эти данные проходят серверную валидацию, контроль ревизии и RLS вместе с самой задачей; отдельная миграция Supabase не требуется. Содержимое файлов в JSON и Supabase не загружается.

Интерфейс позволяет вести ожидаемые и полученные исходные данные, шаблоны, НТД, черновики и готовые документы. Состояния реестра отражают управленческий процесс и не означают, что бинарный файл уже сохранён. После выбора хранилища запись документа получит отдельную защищённую ссылку через адаптер, не меняя текущую модель проекта.

## Локальная файловая библиотека

Для тестового этапа содержимое шаблонов остаётся на компьютере владельца. Серверный адаптер читает корень из `ORBIT_LOCAL_FILES_ROOT`, работает только при обращении по HTTP к loopback-адресу и не включается в Vercel без этой переменной. Каждый запрос проходит существующую авторизацию Orbit; путь канонизируется, выход из корня и переход через символическую ссылку наружу блокируются.

Интерфейс поддерживает навигацию по папкам, скачивание и локальный полнотекстовый поиск. Отдельный индекс хранится в исключённой из Git папке `work/knowledge-index`: в нём находятся технический манифест и извлечённый текст, но нет исходных бинарных файлов. Endpoint поиска работает только на loopback-адресе, возвращает не более 20 результатов и только короткие фрагменты. Путь к тексту из манифеста дополнительно проверяется на выход за пределы индекса.

Первичная индексация поддерживает DOCX, PDF и XLSX. Старые DOC помечаются для последующего преобразования; ошибка обработки одного документа не блокирует остальные. Индекс обновляется отдельной локальной операцией после добавления материалов. Он не отправляется в Supabase, GitHub или Vercel; `/work/` исключён из деплоя как локальный служебный каталог.

Supabase продолжает хранить задачи и метаданные проекта, поэтому локальный рабочий экран видит те же задачи после входа в тот же аккаунт. Публичный Vercel-интерфейс показывает, что локальная библиотека выключена, и не получает путь к диску.

В библиотеке создана версия 0.1 рабочей методики ППР/ТК. Она фиксирует выбор режима «ППР с ТК / без ТК», базовую карту постоянных разделов, матрицу условных приложений, карту запроса исходных данных и правило выделения отличий от шаблона синим шрифтом. Это внутренний стандарт процесса, а не нормативное заключение: ссылки и требования СП должны отдельно подтверждаться будущим специалистом по НТД.

## Агент «Разработчик ППР»: контракт MVP

Первый рабочий сценарий агента ограничен одним выбранным проектом ППР. Агент получает название и описание задачи, заполненный паспорт проекта, перечень метаданных исходных документов и детерминированную карту разделов. Он оценивает полноту исходных данных, предлагает вопросы, поясняет обработку разделов и указывает, какую работу нужно передать другой роли.

До вызова модели сервис сам определяет состав постоянных и условных разделов по сохранённым параметрам: режим ППР с ТК или без ТК, работы на высоте, применение подъёмных сооружений и башенного крана, монолитные работы и источник графиков. Этот расчёт остаётся бизнес-логикой Orbit и отображается даже без OpenAI.

Агент не подтверждает нормативное соответствие, не придумывает требования НТД, не выполняет расчёты опалубки или прогрева бетона, не создаёт схемы AutoCAD, не согласовывает документ и не изменяет задачу автоматически. Нормативные вопросы направляются специалисту по НТД, противоречия — контролёру качества, графика — специалисту AutoCAD, отсутствующие графики и исходные данные — подрядчику или владельцу проекта.

Вызов реализуется официальным OpenAI Agents SDK для TypeScript со структурированным Zod-результатом. Перед каждым вызовом пользователь явно разрешает передачу данных выбранного проекта. Email, JWT, идентификатор владельца, остальные задачи, бинарные файлы и локальный индекс не передаются. Результат первого этапа является предложением и не сохраняется в проект без отдельного подтверждаемого действия.

## ИИ-агенты: первый MVP

### ADR 2026-09-04: черновик одного раздела по локальному шаблону

Используем существующий локальный текстовый индекс и OpenAI Agents SDK 0.17 (MIT), без новой облачной базы поиска и новых зависимостей. Встроенный файловый поиск OpenAI потребовал бы загрузить библиотеку в облако, поэтому для MVP выбран явный выбор локальных фрагментов. Контракт структурированного вывода: https://developers.openai.com/api/docs/guides/structured-outputs.

`/api/work-templates` позволяет выбрать распознанный DOCX/PDF и прочитать текстовые фрагменты. Сервер проверяет границы папок, хеш исходного файла и хеш извлечённого текста. Генерация `/api/agents/ppr-section` получает только идентификаторы выбранных фрагментов (до 8 и 12 000 символов), сверяет хеши и ревизию проекта, а затем после явного согласия отправляет выбранные тексты и паспорт в OpenAI. Остальная библиотека не отправляется. Шаблоны являются недоверенными данными, а не инструкциями агенту. Генерация работает только локально с серверным `OPENAI_API_KEY`; на Vercel доступны ранее сохранённые версии.

Агент готовит один текстовый раздел, не графику, расчёты, ППРк или нормативное заключение. Сервис, а не модель, отмечает синим каждый абзац, который не совпадает дословно с выбранным фрагментом; исходные фрагменты остаются рядом для сравнения. Это сравнение текстовых абзацев, не полная разметка DOCX и не автоматическое подтверждение качества.

Несохранённый результат остаётся в открытом окне. Отдельное подтверждение сохраняет новую версию в `task.pprDrafts` вместе с выбранными фрагментами и их происхождением; интерфейс прямо сообщает о передаче в Supabase. Сохранение проверяет владельца, направление, ревизию, размеры, повторный идентификатор и заново сверяет источники с локальным файлом; до 20 версий и 500 КБ на проект. Поэтому создание и сохранение новой версии выполняются локально, а чтение — также на Vercel. Изменение паспорта не удаляет черновики. Исходные DOCX/PDF никогда не перезаписываются. Экспорт этого этапа — HTML с синими изменениями, не готовый к выпуску DOCX. Откат кода не требует миграции базы; новые поля совместимы со старой моделью задачи. Это дополнение к прежнему реестру метаданных: полный файл не хранится в JSON, но выбранные текстовые фрагменты после отдельного согласия сохраняются вместе с черновиком.

Версии добавляются через API без редактирования ранее сохранённых записей; это история MVP, не защищённый от подмены архив. Пользовательский импорт резервной копии может заменять данные. Общий лимит импорта остаётся 2 МБ; объёмные архивы требуют последующего разделения хранения и резервного копирования. Трассировка SDK отключена, у запроса раздела `store: false`; это не обещание отсутствия иных сроков хранения у провайдера.


Первый агент `task_triage_agent` встроен в существующий сервер Next.js через официальный OpenAI Agents SDK для TypeScript. Отдельный Python-сервис на этой стадии не нужен: это уменьшает число компонентов, сохраняет текущую авторизацию и упрощает публикацию в Vercel. Каждый агент сохраняет одну узкую профессиональную роль; будущий оркестратор будет отвечать за маршрутизацию и совместную работу агентов, не перенося их специализированные функции в одного универсального агента.

Поток данных: пользователь открывает агента под списком сфер → явно разрешает передачу активных задач → защищённый endpoint проверяет JWT → сервер сам загружает задачи и каталог из Supabase → в OpenAI передаются только содержание и параметры задач → структурированные предложения возвращаются в окно проверки. После подтверждения следующий шаг сохраняется отдельной подзадачей со своим сроком; срок всего проекта не меняется. Статусы, сортировка, срочность и счётчики рассчитываются кодом сервиса, а агент лишь предлагает изменения для существующих задач. Email, пароль, идентификатор владельца и история действий не отправляются. Трассировка SDK отключена.

Предложения агента временные и исчезают после перезагрузки страницы. При нажатии «Добавить подзадачу» сервер повторно проверяет ревизию задачи, добавляет следующий шаг как подзадачу с предложенным сроком и сохраняет длительность, приоритет и отметку первой задачи. Срок проекта остаётся прежним, а обоснование сохраняется в истории. «Отклонить» удаляет предложение только из текущего окна.

Модель по умолчанию — `gpt-4o-mini`; её можно заменить серверной переменной `OPENAI_AGENT_MODEL`. Секрет `OPENAI_API_KEY` хранится только в серверном окружении Vercel или локального сервера и никогда не передаётся браузеру. Ключ Vercel не копируется на компьютер автоматически.

## Этапы задачи и напоминания (MVP)

- Подзадачи хранятся внутри JSON-записи родительской задачи в поле `subtasks`. У этапа есть название, дата, время и состояние выполнения. Старые задачи при чтении получают пустой список, поэтому миграция Supabase не нужна.
- Срок родительской задачи остаётся датой завершения всего проекта. Ближайший незавершённый этап используется как дата следующего действия для сортировки и подборок «Сегодня» и «Внимание».
- Завершённый этап больше не влияет на напоминания. Завершение или удаление этапа записывается в историю родительской задачи и сохраняется с проверкой ревизии.
- На текущей стадии напоминание показывается внутри Orbit. Push-уведомления и фоновая доставка требуют отдельного серверного планировщика и разрешения устройства и остаются следующим этапом.

## Жизненный цикл задачи

- Основные статусы: `active` (активная), `waiting` (ожидает действия со стороны), `paused` (приостановлена) и `completed` (завершена). Специальный статус `someday` хранит задачу «до ситуации».
- Только `active` участвует в колесе баланса, сферах, подборке «Сегодня» и фокусе. Остальные статусы остаются в общем списке и могут быть возвращены в активную работу.
- Старые значения `pending` и `running` читаются как `active`, `approval` — как `waiting`, `error` — как `paused`. Данные обновляются при следующем сохранении задачи, отдельная миграция не требуется.
- Показатель «Нужно решить сегодня» считает активные задачи, у которых срок задачи или незавершённого этапа наступил сегодня либо уже просрочен.
